20+models adapted · Jun 2026 – present

Context
The company was moving to multiple chip platforms; the urban NOA stack had to be proven on a new one.
Challenge
As technical lead: hardware bring-up, model migration, validation and iteration, up to a demo ride.
Action
  • Plan: four milestones (platform ready, core functions, vehicle integration, acceptance); behavior first, latency second.
  • Model migration: organized the adaptation of more than 20 models to the new platform, reusing the existing parity checks.
  • Road-test loop: findings grouped by theme, located from recorded data and handed to owners; porting and model issues kept apart.
Result
The urban NOA stack runs on test vehicles with the new platform, with no frame drops on key models, and a demo ride was completed. It laid the groundwork for a multi-platform strategy.

Why this chip, and why early

Our stack ran on Horizon chips. Once Horizon started selling its own driving stack, depending on one chip vendor became a commercial risk. AXERA's M-series offered competitive compute per cost: the M95 (350 TOPS) is comparable to Horizon's J6M class, and few chips above 100 TOPS were available at the time.

Experience with J6M and Qualcomm showed that the value of an adaptation falls month by month. The first teams with a working stack on a new chip get the customer conversations. So the program started before the M95 was ready, on an M97 (700 TOPS) dev board.

Plan

  1. Prove the stack on the dev board, timing second. On the 700-TOPS M97 board, the priority was correct behavior: driving first, then parking. Latency could wait.
  2. Adapt the models. Adapt and quantize each model for the new toolchain, and check numerical consistency with the same stage-by-stage method.
  3. Test on vehicles with the v4 stack, and run development test analysis.
  4. Cluster road-test issues so each goes to the right owner with evidence attached, instead of a list of anecdotes.
  5. Next stage: the target chip. Bring up on the 350-TOPS M95 and tune latency until the driving models fit the frame budget with headroom. This has not been done yet; every on-vehicle result on this page comes from the M97.

Results

The v4 urban NOA stack runs on test vehicles with the M97 dev board. Key models showed no dropped frames in road tests, and latency work continues to add headroom. Bring-up on the target chip, the M95, is the next stage and has no on-vehicle results yet.

Road-test findings were grouped into themes, each with its owner:

  • Lane-change safety: some lane changes came too close to vehicles alongside, or were taken despite traffic approaching from behind.
  • Speed behavior: too conservative on some open roads, and slow to accelerate after yielding to vulnerable road users.
  • Navigation lane choice: wrong lane selection in some scenarios.

These are mostly model-behavior issues, which the model teams continue to improve. Separating "the port is wrong" from "the model needs work" keeps a bring-up moving.

Merging the chip-specific code back into the main branch also exposed integration bugs, which were fixed so the port did not become a long-lived fork.

What this taught me

  • Sequence by value. Correct behavior on a forgiving board first; performance on the target chip comes after.
  • Reuse the method, not just the code. The consistency checks built for Horizon chips transferred directly.
  • Triage is leadership work. Clustering issues with evidence and owners kept a multi-team effort moving.
