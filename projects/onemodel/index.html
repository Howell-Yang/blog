Tech 3aEnd-to-end model training and optimization: faster training and a shared backbone

−54%training time per iteration · 2025 – 2026

Context
Models are moving toward one end-to-end network. Each perception task still carries its own image encoder, and on-vehicle latency caps model size.
Challenge
Train faster, and grow the model within the on-vehicle budget: let the tasks share one image encoder while holding each task's metrics.
Action
  • Faster training: migrated training to PyTorch 2.x and pushed training speed-ups on five models.
  • Shared backbone (design lead, in progress): five perception tasks and 9 cameras are to share the end-to-end model's image encoder, sized by PCA redundancy analysis, with pretraining weights from a closed-form linear solve.
  • Architecture (proposal): wrote an end-to-end driving model design with a distill-then-INT8 path built in from the start.
Result
In the measured occupancy setup (V100, batch 16, AMP), time per iteration went from 1.56 s to 0.71 s (−54%). For the shared design, small-scale comparisons on three tasks are done, each listed metric dropping by less than 2 points. The joint-training flow runs on a small dataset; full joint training and release validation are still to come.
Work in progress. Joint training runs on a small dataset and the losses converge, but the data and the iteration count are still small, and the metrics are below the released single-task models. The latency saving is an estimate.

The problem

On-board latency limits model capacity and frame rate. The latency model showed that the image encoder is the one large module whose cost does not grow with perception range, so it is the part to share.

Phase 1 reused the detection model's backbone directly. The other tasks lost accuracy to varying degrees, occupancy most of all. Phase 2 exists to fix “metrics fall short after merging”.

Structure

  • Shared up to the image neck, not into BEV space for now. The tasks use different BEV ranges and resolutions. Sharing BEV features would mean unifying both, and compute would multiply.
  • Nine cameras at 512 × 1024, with no split between a main and an auxiliary backbone. Fisheye cameras and two rear cameras stay separate for now.
  • The latency budget is rate-weighted. Taking one 10 Hz frame as the unit, a 5 Hz task counts half. Sharing the backbone alone saves about 5 ms per frame; sharing every neck as well saves about 9 ms. Whether the two front-view tasks share a neck accounts for about 4 ms of that. This saving is the budget for a larger backbone.

Sizing the backbone from released models

The width of the new backbone was not chosen by feel.

  1. Extract features stage by stage with the released float checkpoints of the five tasks.
  2. Run PCA on the features to measure how redundant each stage's channels are. Redundant dimensions can shrink; information-dense ones must stay.
  3. Align the channels of the checkpoints, then use PCA to select the dimensions to keep.
  4. Solve for the neck and the per-task projection layers in closed form, which yields a set of pretraining weights.
  5. Check the reconstruction error on held-out clips.

The resulting initial weights already carry most of what the five tasks learned, so joint training does not start from zero.

Two quantization-friendly fixes

  • ReLU6 with a surrogate gradient. From a quantization point of view the activation should be ReLU6, but swapping it in directly hurts training smoothness. The forward pass uses a plain ReLU6. The backward pass replaces its zero derivative in the saturated regions with the derivative of a smooth surrogate.
  • Receptive-field center offset. The original downsampling shifted the center of the receptive field. It is replaced with the common stride-2 plus 2 × 2 convolution, the FPN is kept from adding to the shift, and the sampling grid in the view transform gets the same correction.

How multi-task training is organized

The five tasks do not share data sources, and their labels are not on the same frames. I compared four ways to organize training:

Organization Data and gradient behavior Verdict
Rotate tasks per batch, all GPUs on the same task At each step every GPU draws data for the same task; the shared encoder and that task's head back-propagate Used first. Reuses each task's loader and sampler; tasks are mixed by planned training exposure
Same-source samples, multi-task supervision When one set of cameras has labels for several tasks, shared features run once and the losses are summed An enhancement; requires labels aligned to the same frame, coordinates and augmentation
Mixed tasks within a batch Each sample carries task-validity bits and selects its losses Later; needs changes to task enabling and cross-GPU normalization, a mask alone is not support
Fixed task per GPU Tasks occupy fixed GPU groups; shared parameters sync across groups Not the main line; communication, optimizer and resume are all more complex

One rule runs through all of it: a missing label is never a negative. A task mask only says whether supervision is valid.

Path to release

  1. Single-task restructuring. Each task first moves to the structure it will have in joint training and ships on its own.
  2. Partial merges. Tracking with occupancy; front-view perception with traffic lights (both are image-level features with no BEV transform, so they are easier to merge).
  3. Five-task merge. The backbone is trained jointly and each task ships on the frozen shared encoder. If shared parameters, normalization statistics or quantization boundaries change, a new shared version is cut and every consumer is regression-tested.
  4. Joint perception and planning training.

The main risk is at release: production tolerates very little regression. If a partial merge reaches 90 and the five-task merge only 85, the release stalls. So every step merges only when no task regresses.

One step further: an end-to-end driving model design

This is a design proposal and has not been trained. The numbers in the figure and the text are design values, not measurements.

On top of the shared encoder I wrote an architecture design for an end-to-end driving model. The main choices:

  • The shared encoder is reused unchanged. Its weights, export flow and measured latency stay valid.
  • Tokens on the main path, not a BEV grid. This removes each task's private view transform and gives every loss, planning included, a path back into the encoder.
  • Vision-only input. LiDAR is used to build labels and supervise depth, never as a model input.
  • The plan head outputs control quantities. The path is curvature knots over arc length and speed is acceleration knots over time. Both are rolled out differentiably into a trajectory, so position losses train the knots directly.
  • Navigation enters as tokens built from the SD road network and the route, never from the future ego trajectory, which would leak the label.
  • Deployment is designed in from the start. A fixed-shape graph; distillation to the vehicle model, then INT8 quantization-aware training; and closed-loop metrics, not only open-loop loss, decide whether the quantized model is accepted.

Lessons

  • Share the part that does not change. A module is worth sharing when its cost does not move with the requirement.
  • Let existing models answer questions about the new one. The released checkpoints already hold the answer to how wide each stage should be.
  • Merge only without regression. A multi-task average means nothing; every task has to hold its own metric.
